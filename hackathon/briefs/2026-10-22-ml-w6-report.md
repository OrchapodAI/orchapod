## Item 2: the CPU fallback (no endpoint)
- **Route: the base GGUF + the adapter as a GGUF LoRA, served by llama-server `--lora`, not a merge.** Three reasons:
  1. llama.cpp b11223's images (full and server) ship **no export-lora**: no binary and no `llama` subcommand. A merge would need a llama.cpp source build.
  2. A merge writes a second 16 GB f16 file and then requantizes it. The LoRA is 84–168 MB (f32, r 8–16).
  3. Base and tuned run from the same GGUF file, so the adapter is the only difference.
- **quantize:** new optional input `lora_adapter`, new output `gguf_lora`.
  - It fetches the adapter first (MBs) and requires `adapter_config.json`. An empty tf-finetune adapter (R19) fails before the 16 GB download.
  - Then it runs `convert_lora_to_gguf.py <adapter> --base <model dir> --outfile lora.gguf --outtype f32`. Only the model's config is read.
  - The `base_model.model.` prefix needs no handling: the converter strips it only when present.
  - Metadata adds `type: lora`; metrics add `lora_size_bytes`.
- **judge-eval:** new optional input `tuned_lora` (quantize's `gguf_lora`).
  - It is fetched and checked (`GGUF` magic) before the GGUF refs.
  - The tuned llama-server gets `--lora <file>` over tuned_model_ref's GGUF; every other flag matches the base's.
  - The tuned ModelRef is `{model: <gguf_lora URI>, base_model: <gguf_file URI>}`.
  - These exit 1 before any answer: unresolved ref, a tuned ref that is not a GGUF, or a non-GGUF LoRA.
- **Template 5**, `nebius-docs-specialist-cpu` ("Nemotron Nano docs specialist, judged on CPU"):
  - The same data and training nodes as template 4. Then quantize (Nano, q4_k_m, `lora_adapter`) → judge-eval (base = tuned = `gguf_file`, `tuned_lora` = `gguf_lora`, max_tokens 256 for CPU time).
